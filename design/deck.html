What changed

Editorial instead of soft

The v1 site leaned warm and friendly. This one is ruled, high-contrast, and serif-led — closer to a technical journal than a SaaS landing page.

Why

The claims are now specific

Every feature is listed as implemented, with the one unfinished item (store listing) called out. The layout has to carry evidence, not vibes.

Where

design/v2, unmerged

Lives in the repo, excluded from the Pages workflow. Promoting it is a one-line change once approved.

Read this deck as a proposal. Three decisions at the end need your input; everything else is ready to ship as-is.

Section 1 · revised

Tabs first, not windows

The previous draft led with "windows". Tabbary is a tab manager: windows are an implementation detail of how Chrome groups them.

  • Headline: "Your tabs, kept the way you left them." — the object of the product is the tab.
  • Lede: names groups and windows as scope, not as the subject. "It captures the tabs you are working on — across groups and windows — as a session."
  • Ledger row: "Tab capture" replaces "Session capture", and describes continuous capture rather than window lifecycle.
  • Status card: removed, per your call. Replaced with a four-item ledger strip under the hero (licence, account, host access, sync) so the facts survive without reading as a warning label.

Decision taken: adopt ledger, drop the status card, ship sync in the listing. This slide reflects the revised copy; the live site still shows the old text until you promote design/v2.

Section 2

The feature list becomes a ledger

Eleven rows, each a capability, a one-line description, and a status tag. Ten read "done"; one reads "next".

Why a table

Scannable, and hard to inflate

A card grid invites vague claims. A ledger with a status column forces each row to state whether it exists. The single "next" row is the store listing, which is honest and also creates a reason to come back.

Content source

Generated from the actual repo

Version, test counts, and features come from the working tree: 0.6.0, 195 unit tests, 14 server tests, seven E2E suites. The numbers are verifiable by cloning.

Maintenance cost: this section has to be updated with each release. If that feels like a burden, we can reduce it to five rows and let the changelog carry detail.

Section 3

Four surfaces, drawn once

A single diagram shows the same session list as a popup, a side panel, and a full tab — the clearest argument for the product in one image.

  • Inline SVG, not screenshots. Stays sharp, themes with the page, and weighs about 4 KB.
  • One caption. "One library. The same sessions, rendered for the space you have."
  • Keyboard hints sit next to each surface, because that is how people actually reach them.

The v1 site had a single large screenshot. This version shows the relationship between surfaces instead of one surface in isolation.

Section 4

Privacy, stated as properties

Four claims, each one checkable in the manifest or the source. Then four numbers, because abstract promises are forgettable.

  • No host permissions at install. The extension cannot read pages.
  • History and bookmarks optional. Requested only when used.
  • Sync is ciphertext-only. Key never leaves the device.
  • Export is plain JSON. Readable backup, no lock-in.

7 / 9privacy

Store pack

What a submission still needs

The code is feature-complete for 1.0. What remains is packaging, and three items need decisions only you can make.

  • Real icon set. Current PNGs are placeholders; need 16/32/48/128 + a 1280×800 promo tile.
  • Screenshots. Five, at 1280×800: popup, side panel, full tab, bookmarks, sync settings.
  • Privacy policy page. Short; the manifest makes the claims easy to substantiate.
  • Permission justifications. One sentence per permission, written for a reviewer.
  • Single purpose statement. "Save and restore browser windows as sessions."
Ready

Everything below the listing

Build, tests, icons at correct dimensions (art needed), onboarding, licence, privacy posture, and a working unpacked install path.

Not ready

Anything requiring a decision

Name clearance, a support address, and whether sync ships as part of the listing or as a separate self-hosted add-on.

Decision needed

Three questions before this goes live

Answer these and I can promote the design, generate the store assets, and ship the listing.

01 Direction: adopt "ledger", keep v1, or blend? Ledger is bolder and more honest; v1 is friendlier and already live. Blending usually produces neither.
02 Does the hero keep the status card? It reads as "unfinished by design". Removing it makes the page look more shipped but less specific.
03 Ship sync in the store listing, or document it as an optional add-on? Including it means a reviewer will ask about the server. Excluding it keeps review simple but hides a feature.

Nothing is deployed. When you answer, promoting the site is moving design/v2 over site/ and pushing; the Pages workflow does the rest.
